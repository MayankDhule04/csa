# Security Design

This document explains the security controls implemented in the Terraform code,
mapped to well-known cloud-security principles. It is deliberately specific to
**this** architecture rather than generic advice.

## 1. Security principles applied

- **Network segmentation** — three independent subnet groups (public, private,
  isolated), each with its own route table.
- **Defense in depth** — a request must pass routing rules *and* security group
  rules at every hop; compromising one control does not expose the next tier.
- **Least privilege** — every security group permits exactly one required flow.
- **Attack-surface reduction** — only the ALB is reachable from the internet;
  the app tier has no public IP and the DB has no internet route at all.
- **Secure by default** — encryption at rest on, IMDSv2 required, no SSH, no
  hardcoded secrets.

## 2. Network segmentation

| Subnet group | Route to internet | Purpose |
|--------------|-------------------|---------|
| Public | Inbound + outbound via **IGW** | Load balancer, NAT gateway |
| Private app | **Outbound only** via **NAT** | App servers (patching, AWS APIs) |
| Isolated DB | **None** | Database — cannot reach or be reached by internet |

Because the DB route table has no `0.0.0.0/0` entry, even a misconfigured
security group could not expose the database to the internet — the routing
layer provides a second, independent barrier.

## 3. Security Group design (least privilege)

All inter-tier rules use **security-group references** (source = another SG),
not CIDR ranges. This means "traffic from any instance in the app tier" instead
of "traffic from this IP block", which stays correct if addressing changes and
is tighter than a subnet CIDR.

### `alb-sg` (web tier)
| Direction | Port | Source / Dest | Why |
|-----------|------|---------------|-----|
| Ingress | 80 (TCP) | `allowed_web_cidr` (default `0.0.0.0/0`) | Public web entry point. Tighten to `YOUR_IP/32` for a locked-down demo. |
| Egress | 80 (TCP) | `app-sg` | Forward requests only to the app tier — nothing else. |

### `app-sg` (application tier)
| Direction | Port | Source / Dest | Why |
|-----------|------|---------------|-----|
| Ingress | 80 (TCP) | `alb-sg` | Accept traffic **only** from the load balancer. No direct client access. |
| Egress | 3306 (TCP) | `db-sg` | Reach the database tier only. |
| Egress | 443 (TCP) | `0.0.0.0/0` | HTTPS for patching / AWS APIs (SSM, repos) via NAT. |
| Egress | 80 (TCP) | `0.0.0.0/0` | HTTP for package repositories via NAT. |

### `db-sg` (database tier)
| Direction | Port | Source / Dest | Why |
|-----------|------|---------------|-----|
| Ingress | 3306 (TCP) | `app-sg` | MySQL **only** from the app tier. No public or broad-CIDR rule exists. |
| Egress | — | none defined | SGs are stateful, so responses to the app are allowed automatically; the DB needs no outbound allowance. |

## 4. Identity and access management (IAM)

- The app instances assume a dedicated role (`*-app-role`) rather than using
  long-lived credentials.
- The role attaches `AmazonSSMManagedInstanceCore` for Session Manager access
  (no SSH).
- A tight inline policy grants **read-only** access to the single SSM parameter
  holding the DB password. Its `kms:Decrypt` permission is constrained with two
  conditions rather than left as a broad grant:
  - `kms:ViaService = ssm.<region>.amazonaws.com` — the key may only be used
    when the request is routed through SSM, not via a direct KMS call; and
  - `kms:EncryptionContext:PARAMETER_ARN = <db password parameter ARN>` — SSM
    stamps SecureString decryptions with the parameter's ARN, so this pins the
    decrypt to **exactly** the DB password parameter and no other secret.

  The `Resource` element stays `"*"` only because the AWS-managed SSM key ARN
  cannot be computed without a KMS read permission the deployer may lack; the
  conditions make the effective scope "decrypt only this one parameter, only
  via SSM". No customer-managed KMS key is created, so there is no added cost.
- No IAM users, access keys, or passwords are created or stored in the repo.

## 5. Secrets management

- The RDS master password is generated by Terraform's `random_password` and is
  **never** hardcoded or committed.
- It is stored in **SSM Parameter Store as a SecureString** (encrypted with KMS).
- The application fetches it **at runtime** via its IAM role. The plaintext is
  never written to disk, the web page, or Terraform output.
- `terraform.tfvars` (which could contain overrides) is git-ignored.

> Note: Terraform still records resource attributes in its **state file**, which
> can contain sensitive values. Do not commit `terraform.tfstate`. The provided
> `.gitignore` excludes it. In a team/production setting, use an encrypted
> remote backend (e.g. S3 + DynamoDB lock) — documented as future work.

## 6. Data protection / encryption

| Data | Protection |
|------|------------|
| RDS storage | `storage_encrypted = true` (encryption at rest) |
| EC2 root EBS volume | `encrypted = true` on the launch template |
| DB password | SSM SecureString (KMS-encrypted) |
| Client ↔ ALB | HTTP in this demo (see below); HTTPS recommended in production |

**HTTPS note:** the demo uses an HTTP:80 listener to avoid requiring a domain
and ACM certificate. In production the listener should be HTTPS:443 with an ACM
certificate and an HTTP→HTTPS redirect. This is the one intentional simplification
and is called out so no unsupported "everything is encrypted in transit" claim
is made.

## 7. Compute hardening

- **IMDSv2 required** (`http_tokens = "required"`) to mitigate SSRF-based
  credential theft.
- **No inbound SSH**, no key pair — administration via SSM only.
- **No public IPs** on app instances.
- ALB `drop_invalid_header_fields = true` to discard malformed headers.
- Auto Scaling replaces unhealthy instances automatically.

## 8. Logging, monitoring, backups (customer-configurable)

- RDS **automated backups** retained for 7 days (`backup_retention_period = 7`).
- Additional controls a student can enable to strengthen the project (documented
  as optional to keep cost/complexity down): VPC Flow Logs, ALB access logs to
  S3, CloudTrail, GuardDuty, CloudWatch alarms. These are **customer**
  responsibilities under the shared-responsibility model.

## 9. Honest limitations (no overstated claims)

- Traffic to the ALB is HTTP, not HTTPS, in this demo.
- Logging/monitoring services (CloudTrail, GuardDuty, Flow Logs) are described
  but not enabled by default, to control cost.
- The Terraform state is local by default; treat it as sensitive.
- This is a teaching/demo project, not a production-hardened deployment.
